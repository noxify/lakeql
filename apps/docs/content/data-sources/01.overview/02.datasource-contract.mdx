`@lakeql/datasource` defines the adapter-neutral contracts. It imports nothing engine-specific — no Trino, Fabric, GraphQL, or Kysely — so the core stays independent of any backend.

## The Core Interfaces

- [`DataSource`](/docs/data-sources/overview/api-reference#data-source) — executes SQL, exposes metadata and DDL where supported, and forwards auth and request options to the backend.
- [`DataSourceReadStrategy`](/docs/data-sources/overview/api-reference#data-source-read-strategy) — orchestrates and validates a read.
- [`DataSourceWriteStrategy`](/docs/data-sources/overview/api-reference#data-source-write-strategy) — implements a write path (see [writing](/docs/data-sources/writing)).
- [`AdapterFactory`](/docs/data-sources/overview/api-reference#adapter-factory) — constructs the data source and strategies from a validated connection config.

## Normalized Errors

Adapters translate engine errors into a common hierarchy rooted at [`DataSourceError`](/docs/data-sources/overview/api-reference#data-source-error), each carrying a `category`: `auth`, `query`, `network`, `timeout`, `cancelled`, or `unsupported`. The API layer maps those categories to GraphQL error codes and HTTP statuses, so clients see consistent errors regardless of the engine.

`DataSourceValidationError` is a separate `Error` subclass (not a `DataSourceError`) carrying `field`/`value` rather than a category; it falls through to the generic 500 mapping. See [error handling](/docs/api/customization/error-handling).

## Capabilities

An adapter reports its [`DataSourceCapabilities`](/docs/data-sources/overview/api-reference#data-source-capabilities). A write strategy is only offered when the adapter reports the capabilities it needs — for example, DDL support is not implied by the ability to run `INSERT`.

For the complete contract, see the [API reference](/docs/data-sources/overview/api-reference).
