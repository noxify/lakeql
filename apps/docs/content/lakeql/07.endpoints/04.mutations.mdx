Add a `mutation` block to `endpoint.json` to make the endpoint writable. It's either `false` (explicitly disabled, same as omitting it) or a config object with a `loadStrategy` and a `basePath`.

<ApiReference
  variant="table"
  file="schema-generator/src/endpoint-schema"
  name="MutationConfig"
/>

`loadStrategy` accepts one of three values: `full_load`, `full_load_append`, or `append`. [Load strategies](#load-strategies) below defines each one. `basePath` is required for every one of them, even those that don't use it (see the note below).

### Where the data goes

`basePath` and `partitioning` describe _where inside the configured object store_ this endpoint's data lands and how it is laid out. They do **not** configure the store itself. The bucket, region, and credentials come from the `files-sdk` instance on the data source's `writeConfig`, not from the endpoint. `partitioning` is either `false` (write flat, no partition path) or a partition string that names the fields to lay out by. A bare field name partitions by the raw value (`region=EU`); `Date` and `DateTime` fields are only valid with a component such as `event:year`. The removed `partitioningFormat` key is rejected. For example, with `basePath: "sales/orders"` and `partitioning: "load_timestamp:year/load_timestamp:month/load_timestamp:day"`, an `append` write lands at `sales/orders/all.parquet/year=2026/month=08/day=29/<uuid>.parquet` in whatever bucket the data source is wired to.

See [Writing data](/docs/data-sources/writing) for how the storage write strategy is configured and [Partitioning](/docs/data-sources/writing/partitioning) for the full path layout.

### Auto-fill fields

Partitioning by a write time needs a column that carries that timestamp. Rather than synthesizing one implicitly, declare a field with `options.autoFill`. A write-timestamp auto-fill field is a top-level `DateTime` field:

```json
{
  "name": "load_timestamp",
  "type": "DateTime",
  "options": { "autoFill": "write_timestamp" }
}
```

The server populates it from the write clock on every `append` and `full_load_append` write, and it is **excluded from the mutation input** — clients neither send it nor can override it. It is visible in the GraphQL query type and becomes a real table column, alongside two derived companion columns, `load_timestamp_year` and `load_timestamp_month` (both `Integer`), so you can partition by the extracted components without the client supplying them.

Auto-fill and partitioning are independent. The field is populated and its columns created whenever auto-fill is declared, regardless of `partitioning`; `partitioning` only governs the on-disk path layout. To partition by the derived components, reference the primary field with the component form in the partition string — `load_timestamp:year/load_timestamp:month` — never the companion column names directly. See [Partitioning](/docs/data-sources/writing/partitioning) for the full path layout.

Auto-fill is only valid under an enabled `append` or `full_load_append` mutation; combining it with `full_load`, placing it on a nested or non-`DateTime` field, or declaring it without an enabled mutation is a validation error.

## Load strategies

Set `loadStrategy` to one of three values. Each one picks how a write combines with the data already in the table:

- **`append`** — keep the existing data and add the new records.
- **`full_load`** — replace the existing data with the new records.
- **`full_load_append`** — replace the latest snapshot and keep an appended history alongside it.

These are the config-facing meanings. For the full runtime behavior of each value, see [Load strategies](/docs/data-sources/writing/load-strategies). It covers ordering, atomicity, partial writes, retries, and failure modes.

<Note>
  `basePath` is required by the `mutation` schema regardless of which write
  strategy ends up handling the write. The `basePath` and `partitioning` fields
  are only meaningful for the **storage** write strategy. `full_load` ignores
  partitioning, and the Trino adapter's `INSERT INTO` strategy ignores both — it
  writes directly through SQL — but `basePath` must still be present for the
  definition to validate.
</Note>

## Example

```json
{
  "version": "2.0",
  "catalog": "hive",
  "schema": "sales",
  "tableName": "orders",
  "dataSource": "warehouse",
  "fields": [
    { "name": "id", "type": "Integer", "options": { "required": true } },
    {
      "name": "customerEmail",
      "type": "String",
      "options": { "required": true, "validations": [{ "type": "email" }] }
    },
    { "name": "status", "type": "String", "options": { "readOnly": true } },
    {
      "name": "load_timestamp",
      "type": "DateTime",
      "options": { "autoFill": "write_timestamp" }
    }
  ],
  "mutation": {
    "loadStrategy": "append",
    "basePath": "sales/orders",
    "partitioning": "load_timestamp:year/load_timestamp:month/load_timestamp:day"
  }
}
```

The `load_timestamp` field here is server-populated and excluded from the mutation input; the write lays out under `year=/month=/day=` from its derived components. See [Auto-fill fields](#auto-fill-fields) above.

Generating this definition with [`create-endpoint`](/docs/cli/commands/create-endpoint) also writes a `mutation-schema.ts` file and registers a mutation field in the GraphQL schema, alongside the query field every endpoint gets. See the [mutations guide](/docs/lakeql/guides/mutations) for how that field is authorized and resolved at runtime, or [Set Up a Trino Mutation](/docs/lakeql/guides/set-up-a-trino-mutation) for the end-to-end task.
