LakeQL is organized into layers. Each depends only on the layer below, and the core contracts depend on nothing engine-specific.

```text
Application layer
  API / CLI / create-app / code generator
        │
Composition layer
  config / runtime / adapter registry
        │
Adapter layer
  adapter-trino / adapter-fabric / future adapters
        │
Core contracts
  datasource / query contracts
        │
Infrastructure
  storage / parquet / fabric-client / trino-client
```

## Responsibilities

- **Core contracts** ([`@lakeql/datasource`](/docs/data-sources/overview/datasource-contract)) define neutral interfaces for data sources, strategies, auth, and errors. They import nothing from Trino, Fabric, GraphQL, or Kysely.
- **Adapters** ([Trino](/docs/data-sources/trino), [Fabric](/docs/data-sources/fabric)) own every engine-specific decision: connection, SQL dialect, strategies, and error mapping.
- **Composition** ([`@lakeql/config`](/docs/packages/config)) loads configuration, registers adapter factories, and composes a runtime — without knowing SQL or storage details.
- **Application** ([api](/docs/api), [cli](/docs/cli)) consumes only the runtime and the core contracts. It does not import adapter packages for normal runtime decisions.

## Why It's Layered This Way

A new adapter provides its own connection, read, write, SQL, and response logic without changing any core package. The registration is explicit — adapters are passed into `defineConfig`, never discovered implicitly and never augmenting the config package through module augmentation. See the [package map](/docs/lakeql/introduction/package-map) for how the packages map onto these layers.
