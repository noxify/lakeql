A single GraphQL request moves through these stages:

<Steps>

<Step>Authenticate</Step>

The [token resolver](/docs/api/authentication/jwt-authentication) validates the request's token into a current user, and the identity resolver maps it to a resolved identity (including whether the caller is a service principal).

<Step>Authorize</Step>

[Scope authorization](/docs/api/authentication/scope-authorization) checks the field's required scopes — authenticated, read permission, write permission — against the context before the resolver runs.

<Step>Resolve credentials</Step>

The runtime's auth resolver produces request-scoped credentials for the target data source, applying any [impersonation resolver](/docs/api/authentication/trino-user-impersonation) (per-source, then global).

<Step>Build and run</Step>

The [query builder](/docs/packages/query-builder) builds the SQL from the GraphQL selection; the adapter renders and executes it against the engine.

<Step>Transform and respond</Step>

The response is decoded and transformed into typed records, and returned with pagination metadata.

</Steps>

## Errors

Anything that fails along the way becomes a normalized error: the adapter throws a typed `DataSourceError`, which the API maps to a GraphQL error with a stable code and HTTP status, logs server-side, and forwards to the `onError` hook. See [error handling](/docs/api/customization/error-handling).

## Shutdown

The runtime owns the data-source connections. When the process receives a shutdown signal, the application calls `runtime.close()` to release them. See the [runtime lifecycle](/docs/lakeql/configuration/runtime-lifecycle).
