A single GraphQL request moves through these stages:

<Steps>

<Step>Authenticate</Step>

The [token resolver](/docs/api/authentication/jwt-authentication) validates the request's token into a current user. The identity resolver then maps it to a resolved identity, including whether the caller is a service principal.

<Step>Authorize</Step>

Before the resolver runs, [scope authorization](/docs/api/authentication/scope-authorization) checks the field's required scopes against the context. Those scopes are authenticated, read permission, and write permission.

<Step>Resolve credentials</Step>

The runtime's auth resolver produces request-scoped credentials for the target data source. It applies any [impersonation resolver](/docs/api/authentication/trino-user-impersonation), per-source first, then global.

<Step>Build and run</Step>

The [query builder](/docs/packages/query-builder) builds the SQL from the GraphQL selection. The adapter renders it and executes it against the engine.

<Step>Transform and respond</Step>

LakeQL decodes the response, transforms it into typed records, and returns it with pagination metadata.

</Steps>

## Errors

Anything that fails along the way becomes a normalized error. The adapter throws a typed `DataSourceError`. The API maps it to a GraphQL error with a stable code and HTTP status, logs it server-side, and forwards it to the `onError` hook. See [error handling](/docs/api/customization/error-handling).

## Shutdown

The runtime owns the data-source connections. When the process receives a shutdown signal, the application calls `runtime.close()` to release them. See the [runtime lifecycle](/docs/lakeql/configuration/runtime-lifecycle).
