Authorization is enforced at the schema level through Pothos's scope-auth plugin. Each generated field declares the scopes it requires, and the builder evaluates them against the request context before the resolver runs.

## The Scopes

The schema builder defines three auth scopes:

- `authorized` — true when there is an authenticated current user.
- `readPermission` — checks read access for the field's data source, catalog, schema, and table.
- `writePermission` — the same, for writes.

`readPermission` and `writePermission` delegate to the resolvers on your config ([`hasReadPermission`](/docs/api/authentication/permissions) / `hasWritePermission`), falling back to the built-in checks. The two are not symmetric — see the default behavior below.

## Evaluation

The default strategy is `any`, and errors during scope evaluation are treated as unauthorized. When authorization fails, LakeQL surfaces the first underlying error — including a permission-denied (403) from the data source — rather than a generic message. See [error handling](/docs/api/customization/error-handling).

## Default Behavior

The two permission scopes default differently:

- **`readPermission`** — when no matching rule exists, a human user is allowed (the adapter enforces its own access control) and a service principal is denied. The identity resolver flags which one the caller is, keeping machine callers least-privilege by default.
- **`writePermission`** — denied for everyone without an explicit matching `Mutation` rule, regardless of principal type. Writes are opt-in.

See [permissions](/docs/api/authentication/permissions) for how to declare rules.
