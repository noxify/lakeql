Permissions declare what a technical user may read and write, scoped by data source, schema, and table. You pass an array of `Permission` rules to the server via [`defineApiConfig`](/docs/api/server-setup/define-config).

```ts
import type { Permission } from "@lakeql/config"
import { createPermission } from "@lakeql/api/helpers"

export const permissions: Permission[] = [
  {
    name: "reporting-user",
    useSystemUser: false,
    permissions: {
      Query: [
        createPermission("warehouse", (rule) => [
          rule({ schema: "sales", tables: ["orders"] }),
        ]),
      ],
      Mutation: [],
    },
  },
]
```

## Building Rules

[`createPermission`](/docs/api/api-reference#create-permission) builds a rule scoped to one data source. The callback receives a `rule` builder; each `rule({ schema, tables })` grants access to the listed tables within a schema. Group rules under `Query` (reads) and `Mutation` (writes).

### Wildcards and Scope Matching

Rules support wildcards: `schema` accepts `"*"` to match any schema, `tables` accepts `["*"]` to match any table, and omitting `catalog` matches any catalog.

Scope matching is strict: a rule that names a concrete `catalog` or `schema` matches only a request whose target carries the same value. A target that omits `catalog`/`schema` does not match a rule scoped to one — the rule's scope is never silently ignored. Use `"*"` (schema) or an omitted `catalog` to match broadly on purpose.

<Note>
  The `name` field matches the resolved user name, and `useSystemUser` is part
  of the `Permission` shape but currently has no behavioral effect.
</Note>

## Default

Reads and writes default differently when no matching permission entry exists:

- **Reads** — a human user is allowed (the adapter layer enforces its own access control); a service principal is denied.
- **Writes** — denied for everyone. Writes require an explicit `Mutation` rule that matches the target; without one, the write is rejected regardless of principal type.

So an empty `permissions` array lets human users read, but no one can write until you add `Mutation` rules.

## Custom Resolvers

For logic beyond the declarative rules, provide `hasReadPermission` / `hasWritePermission` resolvers on the config. They override the built-in checks. See [`ReadPermissionResolver`](/docs/api/api-reference#read-permission-resolver) and [`WritePermissionResolver`](/docs/api/api-reference#write-permission-resolver).
