For advanced use cases that don't fit the endpoint builder pattern, you can write schema fields manually using the Pothos builder. This gives you full control over types, resolvers, and authorization.

<Note>
  For most endpoints, the [CLI endpoint
  builder](/docs/api/customization/custom-queries-mutations) is the recommended
  approach. Use manual fields for cross-cutting concerns (health checks, cache
  management, aggregation queries) that don't map to a single table.
</Note>

## File discovery

The schema loader scans for files matching these patterns in the configured `schemaPath` directory:

```
schemas/**/query-schema.{ts,js,mjs}
schemas/**/mutation-schema.{ts,js,mjs}
**/query-schema.{ts,js,mjs}
**/mutation-schema.{ts,js,mjs}
```

Any file named `query-schema.ts` or `mutation-schema.ts` that uses the shared builder will have its types registered automatically.

## Adding a custom query field

```ts path="src/schemas/manual/query-schema.ts"
import { builder } from "@lakeql/api/builder"

builder.queryField("serverInfo", (t) =>
  t.field({
    type: "String",
    description: "Returns the current server version",
    resolve: () => "1.0.0",
  })
)
```

## Adding a custom mutation field

Mutation fields use `builder.mutationField`. The mutation type is registered automatically by the API server when mutation schema files are detected — you don't need to call `builder.mutationType({})` manually.

```ts path="src/schemas/manual/mutation-schema.ts"
import { builder } from "@lakeql/api/builder"

builder.mutationField("refreshCache", (t) =>
  t.field({
    type: "Boolean",
    description: "Invalidates the internal cache",
    authScopes: {
      authorized: true,
    },
    resolve: async (_parent, _args, context) => {
      context.logger.info(
        "Cache refresh triggered by",
        context.currentUser?.userName
      )
      // perform cache invalidation
      return true
    },
  })
)
```

## Custom types with arguments

```ts path="src/schemas/analytics/query-schema.ts"
import { builder } from "@lakeql/api/builder"

const MetricResult = builder
  .objectRef<{
    name: string
    value: number
    timestamp: Date
  }>("MetricResult")
  .implement({
    fields: (t) => ({
      name: t.exposeString("name"),
      value: t.exposeFloat("value"),
      timestamp: t.expose("timestamp", { type: "DateTime" }),
    }),
  })

builder.queryField("metrics", (t) =>
  t.field({
    type: [MetricResult],
    args: {
      name: t.arg.string({ required: true }),
      from: t.arg({ type: "DateTime", required: true }),
      to: t.arg({ type: "DateTime", required: true }),
    },
    authScopes: {
      readPermission: {
        catalog: "hive",
        schema: "analytics",
        tableName: "metrics",
      },
    },
    resolve: async (_parent, args, context) => {
      // Query Trino or any other data source
      return []
    },
  })
)
```

## Auth scopes

LakeQL provides three built-in auth scopes you can use in manual fields:

| Scope | Description |
| --- | --- |
| `authorized` | User must be authenticated |
| `readPermission` | User must have read access to the specified catalog/schema/table |
| `writePermission` | User must have write access to the specified catalog/schema/table |

```ts
authScopes: {
  writePermission: {
    catalog: "hive",
    schema: "analytics",
    tableName: "events",
  },
}
```

## Directory structure

Place manual schema files in a separate directory to keep them distinct from generated code:

```
src/schemas/
├── generated/          # Auto-generated by `lakeql-cli pull`
├── custom/             # Auto-generated by `lakeql-cli create-endpoint`
└── manual/             # Hand-written schemas
    ├── query-schema.ts
    └── mutation-schema.ts
```

<Warning>
  Don't modify files in `generated/` or `custom/` — they will be overwritten by
  the CLI. Put custom logic in `manual/` or another directory of your choice.
</Warning>
