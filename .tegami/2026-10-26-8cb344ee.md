### Per-data-source paging configuration

Paging limits are now configured per data source instead of through a single process-global API knob. Each data-source entry accepts optional `defaultPerPage` and `maxRecordsPerPage` fields, and the top-level config accepts a `paging` block with the same fields as global defaults.

Each field is resolved independently by precedence: the per-source value wins, then the config-level global default, then the system default (`100` for `defaultPerPage`, `2000` for `maxRecordsPerPage`). These limits flow from config into each adapter's read strategy and are enforced at the read layer, so the maximum page size is applied regardless of what a GraphQL request asks for.

When a GraphQL query omits `perPage`, the request passes through to the read strategy without a value and the data source's resolved `defaultPerPage` applies. The generated resolver no longer bakes in a `?? 100` fallback.

Config loading fails fast when a resolved `defaultPerPage` exceeds its resolved `maxRecordsPerPage`. Watch for the case where a per-source `maxRecordsPerPage` of `50` is combined with the system default `defaultPerPage` of `100`: that pairing now raises a config error naming the source and the offending values, so set `defaultPerPage` at or below `maxRecordsPerPage`.

**Breaking:** the obsolete API-layer paging surface is removed. The `maxRecordsPerPage` option on `ApiRuntimeConfig`, the `API_MAX_RECORDS_PER_PAGE` environment variable, and the `setMaxRecordsPerPage` export from `@lakeql/api` no longer exist. Configure paging per data source instead.
