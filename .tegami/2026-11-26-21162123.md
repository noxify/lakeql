### Endpoint write method: storage or insert

An endpoint's `mutation` block takes an optional `writeMethod`, either `"storage"` or `"insert"`. An absent value means `"storage"`. With `"storage"`, `basePath` is required, and partitioning and auto-fill work as before. With `"insert"`, the schema rejects `basePath`, a partition string and auto-fill fields, because the Trino `INSERT INTO` strategy uses none of them. Validation errors inside `mutation` now report their exact path, for example `mutation.writeMethod`, instead of a generic `Invalid input` at `mutation`. `@lakeql/schema-generator` exports `flattenEndpointIssues` and `effectiveWriteMethod` for this.

Generated code carries the method into the write config (`DataSourceWriteConfig.writeMethod`). The Trino storage and insert strategies throw before any write when the endpoint's method does not match the data source's `writeConfig.strategy`. The Trino insert strategy also rejects a `basePath`, a partition string or `autoFillFields` in its write config instead of ignoring them. `create-endpoint` shows the method in its summary and generates a resolver that references only the `storageConfig` keys it emits, which fixes a type error for `full_load` endpoints with a partition string.

#### Migration

Endpoints that target a data source with `writeConfig.strategy: "insert"` must set `mutation.writeMethod: "insert"` and remove `basePath`, then be regenerated with `create-endpoint`. Without it, the endpoint defaults to `storage` and every write fails with the mismatch error.
