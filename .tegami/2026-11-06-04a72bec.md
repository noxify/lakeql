### Add `createLakeQLApp`, a near plug-and-play app entry point

`@lakeql/api` now exports `createLakeQLApp`, a convenience wrapper that collapses the standard server wiring a generated `src/index.ts` would otherwise hand-write. It loads the project config (or accepts an already-loaded `project`), derives the per-source auth metadata and global impersonation resolver, builds the `ResolveAuth` via `createApiResolveAuth`, composes the runtime via `createLakeQLRuntime`, and defines the server via `defineApiConfig`. Permissions default to `project.config.auth?.permissions ?? []` (overridable) and the empty-permissions warning now lives inside the wrapper.

Every `defineApiConfig` option is forwarded through (`tokenResolver`, `identityResolver`, `hasReadPermission`, `hasWritePermission`, `permissions`, `cors`, `onError`, `yogaConfig`, `port`, `baseDir`, `schemaPath`, `graphqlPath`, `healthCheckEndpoint`), so you never have to eject just to tweak one option. It returns `{ runtime, start, close }` and registers `SIGTERM`/`SIGINT` shutdown by default via `handleSignals` (set `false` to own the lifecycle yourself). `defineApiConfig` remains the underlying primitive, and the docs include an eject example that is byte-for-byte the wrapper's internals.

### Scaffolded apps use `createLakeQLApp`

The generated app's `src/index.ts` is now a slim file that imports `createLakeQLApp` from `@lakeql/api/create-app`, passes its `tokenResolver`, and starts the server. Config-sourced permissions and the empty-permissions warning are handled by the wrapper, so the entry file no longer hand-wires `loadConfig` → `createApiResolveAuth` → `createLakeQLRuntime` → `defineApiConfig`. A comment links to the docs eject section for users who want full control.
